# Dispatch fence integration QA

This patch targets Postiz `8b84b0dc2767b757c2355158573635600ae027c7` (self-hosted v2.24.0). Use Node 22 and PNPM 10.6.1. Existing workflow definitions and existing activity signatures remain unchanged. The new `postWorkflowV113` wraps frozen V112 provider handling with one durable claim before any provider publishing activity.

`Post.dispatchControl` is NULL for legacy posts, ARMED only for explicitly enrolled new single unpublished drafts, CLAIMED once one workflow execution acquires dispatch, and STOPPED if cancellation wins first. Claim and stop compare-and-set the same PostgreSQL row. STOPPED is permanent, regardless of workflow start, retry, timer, termination or visibility failures. CLAIMED can never produce a positive stop receipt, including after a failed or timed-out provider activity. Private date/status edits and public/private upserts cannot rearm either state. No shipped workflow has changed and no activity parameter has changed.

The authenticated public capability endpoint advertises `dispatch-fence-v1` only when `POSTIZ_DISPATCH_FENCE_ENABLED=true`. An opted-in draft is created through the existing validated/entitled POST `/public/v1/posts`, with top-level `deliveryControl: "dispatch-fence-v1"`; opt-in accepts only a new, single, nonrepeating unpublished draft without caller post IDs or groups. Normal scheduling retains the gate and selects V113. The missing-post sweeper also selects V113. Other API consumers and legacy schedules retain their existing workflows.

POST `/public/v1/posts/:id/stop` takes `{requestId,binding,integrationId,content,images,scheduledAt}`. It binds the original root/content/uploaded images/account/time. A positive stop rejects legacy, changed, threaded, grouped, repeating, deleted, released or near-time records. A claimed dispatch can record only UNCONFIRMED, including after the scheduled instant, failure or publication; that negative receipt never changes delivery or unlocks a replacement. The immutable receipt echoes the bound post/account/time/operation with STOPPED and a timestamp, or UNCONFIRMED after a dispatch claim. Repeating the same command returns the same receipt; a different operation or binding cannot take ownership. GET `/public/v1/posts/:id/stop/:requestId` is read-only and recovers a lost acknowledgement. Authentication and organization selection use the existing public middleware; there is no customer-supplied organization override added here.

## Local tests only

Use an isolated external-drive checkout and a disposable local database. The integration tests refuse every database URL except the one below. No account token, live channel, paid API or protected QA draft is used. The HTTP fixture supplies a synthetic organization through test middleware; production public authentication is unchanged and remains registered on both public controllers.

1. [ ] Install the lockfile with `pnpm install --frozen-lockfile --ignore-scripts`, then run `pnpm exec prisma generate --schema libraries/nestjs-libraries/src/database/prisma/schema.prisma`.
2. [ ] Create a disposable database directory outside synced folders: `mkdir -p .orbit/tmp/temporal-server` and `initdb -U sivants -D .orbit/tmp/stop-proof-postgres -A trust --no-locale`. Start it using `pg_ctl -D .orbit/tmp/stop-proof-postgres -l .orbit/tmp/stop-proof-postgres.log -o '-h 127.0.0.1 -p 55439 -k /tmp' start`. These commands are for the disposable test database only.
3. [ ] Set `DATABASE_URL='postgresql://sivants@127.0.0.1:55439/postgres?schema=stop_proof'`, then run `pnpm exec prisma db push --schema libraries/nestjs-libraries/src/database/prisma/schema.prisma`. Confirm the output names localhost:55439 and schema stop_proof.
4. [ ] Run `pnpm run test:delivery-stop:db`. Expect seven passing tests, including 100 races using two independent Prisma clients, lost/repeated receipts, organization isolation, DTO rejection, legacy/group/thread/repeat refusals, immutable upsert/date/status guards, and late claimed receipts after due time, failure and publication.
5. [ ] Run `pnpm run test:delivery-stop:workflow`. The bundle helper overrides the upstream developer-specific SWC baseUrl only for this local build. The SDK downloads its official ephemeral test server into `.orbit/tmp/temporal-server`. Expect `PASS actual Temporal worker: stop-before-dispatch` with zero provider mutations and `PASS actual Temporal worker: dispatch-before-stop` with a past-due schedule, an UNCONFIRMED receipt and one synthetic publishing activity. Provider network publishing is stubbed; the Temporal worker, timers, activity context, fence and Prisma operations are real.
6. [ ] Run `pnpm run typecheck:provider`, `pnpm run lint:provider`, `pnpm run lint`, `pnpm run test:provider-security` and `pnpm run audit:security` from the repository root. Expect clean backend/orchestrator typechecks, zero errors/warnings for strict provider lint, zero full-root lint errors (existing frontend adoption warnings remain), sixteen passing security/compatibility tests, and zero unmitigated high/critical findings. The one raw braces high remains visible and is accepted only after the exact locked patch/source hashes and attack regressions pass.
7. [ ] Run `pnpm run build:backend`, `pnpm run build:orchestrator`, `pnpm --filter ./apps/frontend run build` and `pnpm run build:extension`. Expect all builds to succeed under Node 22.22.0 / PNPM 10.6.1.
8. [ ] Stop the disposable database with `pg_ctl -D .orbit/tmp/stop-proof-postgres stop`. Keep existing protected/live QA records untouched.

## Release prerequisites for later review — not performed

Apply only the additive provider schema change to the existing Postiz database after backup/review; no StudioAnchor shared schema or identity table changes are needed. Build and update **every** API instance, orchestrator worker and missing-post sweeper before setting `POSTIZ_DISPATCH_FENCE_ENABLED=true` on the API. Mixed old/new binaries are unsafe: an old API or sweeper could select V112 for an enrolled row and bypass the fence. Keep the capability disabled until that rollout is complete. Do not roll back to old binaries while any enrolled posts exist; drain/reconcile them or retain this fence-compatible code first.

Legacy schedules are deliberately not certified retroactively: there is no evidence that an older worker has not already cached a publishing activity. They remain assisted/unconfirmed. Provider deletion, a missing calendar row, Temporal visibility, or successful termination alone cannot release a replacement. Preserve stopped root rows and their durable receipts; do not purge/reuse their IDs. No merge, host migration, capability enablement, deployment, live schedule or live cancellation was performed for this change.
